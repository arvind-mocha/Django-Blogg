# Django Blog

A Django blog with registration, login, password reset, author-only post editing
and deletion, pagination, and profile pictures. Uses Python 3.12, Django 5.2 LTS,
Gunicorn, WhiteNoise, and SQLite. No AWS account is required.

## Run with Docker

Install Docker with Compose v2 and start Docker Desktop if using macOS or Windows.
Use a POSIX shell (WSL or Git Bash on Windows). From this repository:

```sh
sh scripts/setup.sh
docker compose up --build -d --wait
```

Open **http://localhost:8000** and register an account. The setup script creates
an ignored `.env` with a unique random secret and private file permissions. It
preserves an existing `.env`. Never commit or share this file.

The first startup applies migrations and collects static files automatically.
The app runs as UID 10001, with capabilities dropped. SQLite and uploaded images
live in the named `blog_data` volume and survive container replacement. The
published port is bound to the host's loopback interface.

```sh
docker compose exec web python manage.py createsuperuser
docker compose logs --tail=100 web
docker compose stop
docker compose up -d --wait
```

The admin is at `/admin/`. Use `docker compose down` to remove the containers;
**adding `--volumes` deletes the database and uploads**. The health check verifies
the server accepts TCP connections; use an HTTP monitor for full availability.

Password reset emails appear in local container logs. That includes the reset
link: keep logs private and configure SMTP for a public deployment.

## Configuration

Copy the names from [.env.example](.env.example). Boolean values must be `true`
or `false`. Django requires a random `SECRET_KEY` of at least 50 characters and
refuses empty keys or wildcard hosts. Keep the same secret across restarts.

| Variable | Purpose |
| --- | --- |
| `SECRET_KEY` | Signing key, generated by the setup script; keep private |
| `DEBUG` | Defaults to false; enable only during local development |
| `ALLOWED_HOSTS` | Comma-separated hostnames, without schemes or ports |
| `CSRF_TRUSTED_ORIGINS` | Comma-separated full origins, including scheme and any nonstandard port |
| `DATA_DIR` | Persistent files; Compose fixes this at `/app/data` |
| `SECURE_SSL_REDIRECT` | Redirect HTTP requests to HTTPS |
| `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE` | Send cookies only over HTTPS |
| `SECURE_HSTS_SECONDS` | Browser HTTPS policy duration; local HTTP uses 0 |
| `TRUST_PROXY_HEADERS` | Trust a proxy's overwritten `X-Forwarded-Proto` header |
| `EMAIL_BACKEND` | Console locally; SMTP in production |
| `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_USE_TLS` | SMTP server and STARTTLS settings |
| `EMAIL_USER`, `EMAIL_PASS`, `DEFAULT_FROM_EMAIL` | SMTP credentials and verified sender |

The example intentionally disables HTTPS enforcement for **local HTTP** while
keeping `DEBUG=false`. With no overrides, the application defaults to HTTPS and
secure cookies. `.env` is loaded by Compose; direct Python commands need the
variables exported into their environment.

## Deploy on a server

This setup targets one server and one application container with a persistent
volume. SQLite suits a small blog. For multiple instances or sustained concurrent
writes, add a PostgreSQL backend and shared object storage before scaling.
Hosts with ephemeral disks need an attached persistent volume.

1. Install Docker/Compose on the server, clone the repository, and run
   `sh scripts/setup.sh`. Point your domain's DNS to the server.
2. Edit the server's private `.env` with your domain and these HTTPS settings:

   ```dotenv
   DEBUG=false
   ALLOWED_HOSTS=blog.example.com
   CSRF_TRUSTED_ORIGINS=https://blog.example.com
   SECURE_SSL_REDIRECT=true
   SESSION_COOKIE_SECURE=true
   CSRF_COOKIE_SECURE=true
   SECURE_HSTS_SECONDS=31536000
   TRUST_PROXY_HEADERS=true
   EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend
   EMAIL_HOST=smtp.your-provider.example
   EMAIL_PORT=587
   EMAIL_USE_TLS=true
   EMAIL_USER=your-smtp-user
   EMAIL_PASS=your-smtp-password
   DEFAULT_FROM_EMAIL=blog@your-domain.example
   ```

   Keep the generated `SECRET_KEY`. Replace the example email values with real
   provider settings. A Gmail account needs an app password where supported.
   If using only implicit TLS on port 465, adapt the email settings; this example
   configures STARTTLS on port 587.
3. Terminate HTTPS with a trusted reverse proxy on the same host. An Nginx
   configuration is provided at [docker/nginx.conf.example](docker/nginx.conf.example).
   Install Nginx and provision a valid TLS certificate through your certificate
   provider (for example, Let's Encrypt), replace its example domain/certificate
   paths, and load it in Nginx's `http` context. Validate with `nginx -t` before
   reloading Nginx. The example requires an existing certificate; it does not
   issue one. Expose only ports 80/443 through the firewall.
4. Keep port 8000 on loopback. The proxy must **overwrite** client-supplied
   forwarding headers before enabling `TRUST_PROXY_HEADERS`. The example also
   limits authentication requests, caps request bodies at 6 MB, and excludes URL
   paths/query strings from access logs so reset tokens are not logged. Apply
   equivalent controls if using another proxy.
5. Run `docker compose up --build -d --wait`, then
   `docker compose exec web python manage.py check --deploy`. Review its output.
   HSTS subdomain/preload warnings require a domain-specific decision: enable
   `SECURE_HSTS_INCLUDE_SUBDOMAINS=true` and `SECURE_HSTS_PRELOAD=true` only if all
   relevant subdomains permanently support HTTPS and you intend to opt in.
6. Create an administrator, verify login/logout, create/edit/delete a post,
   upload an avatar, and send a real password reset email over HTTPS. Configure
   backups and availability monitoring.

Authentication throttling is provided by the example proxy. Django itself does
not impose a failed-login limit. Do not expose the application directly to the
internet without equivalent rate limits, including `/admin/login/`.

To update, back up first, pull the new code, and run:

```sh
docker compose up --build -d --wait
```

Startup applies new migrations, so assess migration compatibility before rolling
back an image. Rebuild periodically to pick up base-image security updates.

## Back up and restore

Backups contain account data and images: store them privately and encrypt remote
copies. These commands stop writes briefly and archive the complete volume.
`backups/` is ignored by Git and Docker.

```sh
umask 077
mkdir -p backups
docker compose stop web
docker compose run --rm --no-deps -T web python -c \
  "import sys,tarfile; t=tarfile.open(fileobj=sys.stdout.buffer, mode='w|gz'); t.add('/app/data', arcname='data'); t.close()" \
  > backups/blog-data.tar.gz
docker compose start web
```

To restore a trusted backup into an initialized volume, stop the app, extract as
the application user, then start it again. Restore also works on a fresh checkout
after generating its `.env`. Retain that deployment's original secret separately
if existing sessions and reset links must remain valid.

```sh
docker compose stop web
docker compose run --rm --no-deps -T web python -c \
  "import sys,tarfile; t=tarfile.open(fileobj=sys.stdin.buffer, mode='r|gz'); t.extractall('/app', filter='data')" \
  < backups/blog-data.tar.gz
docker compose up -d --wait
```

## Local development without Docker

Use Python 3.12 on macOS/Linux, or equivalent commands in your shell:

```sh
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
chmod 600 .env
python -c 'import secrets; print(secrets.token_urlsafe(64))'
```

Paste the generated value into `SECRET_KEY` in `.env`, then:

```sh
chmod 600 .env
set -a
. ./.env
set +a
export DEBUG=true
mkdir -p data
python manage.py migrate
python manage.py runserver
```

Use the development server only locally. `DEBUG=true` should never be used for
public hosting. Do not use `Mysite.test_settings` in a deployed server: it uses a
fast, insecure password hasher exclusively for isolated tests.

## Checks

```sh
docker compose exec web python manage.py test --settings=Mysite.test_settings
docker compose exec web python manage.py makemigrations --check --dry-run
```

For a dependency audit, activate your local virtual environment, install
`pip-audit`, and run `pip-audit -r requirements.txt --no-deps --disable-pip`.
CI runs the tests, audit, production configuration checks, container build,
private-file checks, and a live HTTP request on each push and pull request.

## Existing data and security review

The old root database and uploaded media are no longer tracked or copied into
images. Existing local copies were preserved. New installations start empty in
`data/` or the Docker volume. To reuse an old database, make a private backup and
copy it to the configured data directory while the app is stopped, then migrate.
Legacy avatar paths should be cleared and images reuploaded through the new
validation; do not import unvalidated legacy media. S3 is no longer configured.

See [SECURITY.md](SECURITY.md) for findings, changes, and the remaining exposure
in previously published Git history. User passwords from the historical database
must be treated as compromised even though Django stored hashes.
